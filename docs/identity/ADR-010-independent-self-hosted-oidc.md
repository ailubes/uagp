# ADR-010. Незалежна самостійно розгорнута ідентифікація UAGP

**Статус:** архітектурна пропозиція, 22.11.2026. Запропоноване рішення – **самостійний OIDC-провайдер UAGP без зв'язку з Wesfin ID**. Конкретне ПЗ, домени, оператори, бюджети та впровадження залишаються предметом окремого рішення.

## Контекст

UAGP має бути громадянською спільною інфраструктурою, а не продуктом приватної компанії. Використання ідентифікації іншого бізнесу створило б залежність від адміністратора, його комерційних політик, фінансування та можливості відкликати доступ.

У формулюванні «окремий self-hosted OIDC client» потрібно розрізняти ролі: **OpenID Provider (issuer)** – самостійно розгорнутий сервер ідентифікації, тоді як **OIDC clients** – окремі застосунки UAGP, зареєстровані в ньому (web portal, адміністрування тощо). Віддалений MCP – окремий захищений ресурс, якому потрібен OAuth-контур авторизації. Один лише OIDC-login не створює прав для MCP.

## Запропоноване рішення

1. **Незалежний провайдер ідентичності UAGP** у власному контурі, з власними ключами, базою, резервним копіюванням, операторами та правовою відповідальністю. Ніяких токенів, клієнтських секретів, спільних realm, таблиць користувачів, адміністративних облікових записів, залежностей чи федерації з Wesfin ID.
2. **Окремі клієнти UAGP** із мінімальними правами. Для браузера – Authorization Code + PKCE S256, сувора перевірка issuer, audience, exp, nonce/state, exact redirect URIs, server-side сесії та належний захист cookie/CSRF; без Implicit Flow і Resource Owner Password.
3. **Окрема прикладна авторизація**: OIDC підтверджує технічний обліковий запис, але UAGP визначає права діяти в конкретній процедурі й може відмовити навіть із чинним токеном. Токен не дає автоматичних прав на публікацію, модерацію або зміни Harness.
4. **Read-only участь без входу**: Хартію, відкриті протоколи й законно оприлюднені пропозиції можна читати без акаунта. Для створення приватної справи потрібно окремо визначити мінімально необхідний рівень автентифікації. Для майбутніх офіційних процедур і голосування – законна перевірка права участі, відокремлена від простого OIDC.
5. **Псевдонімність за замовчуванням у відкритій дискусії**: не публікувати стабільні ID акаунтів у GitHub, федеративних подіях чи відкритому каталозі. За можливості використовувати sector-specific / pairwise ідентифікатори, уникати кореляції поведінки між різними сервісами.
6. **Незалежність як організаційна умова**: ключі, домени, кошти й оператори не повинні належати єдиному невідкличному приватному адміністратору. Потрібні публічна модель відповідальності, контроль доступів, процедура зміни оператора, переносимість акаунтів у законному обсязі й незалежний аудит.
7. **Захист даних та доступність**: мінімальні дані, чіткі строки зберігання, доступ до власних даних, процедури виправлення/видалення, резервні канали для людей без смартфонів, офлайн-допомога та захист від захоплення акаунтів.

## Remote MCP

Віддалений MCP має спиратися на стандартизований OAuth-захист, захищений сервер авторизації, discovery, правильну аудиторію токенів та обмежені scopes. Запуск ресурсу MCP, використання власної LLM і право на юридично значущу дію – **три різні речі**. Жоден із цих статусів не випливає автоматично з іншого.

Модель громадянина не повинна отримувати його пароль, refresh token чи адміністративні дозволи. Кожен інструмент має окрему межу доступу, а для write-операцій потрібні вузькі scope, належне підтвердження та прикладний контроль права.

## Що не вирішено цією ADR

- Конкретний вибір self-hosted ПЗ (Keycloak, Authentik або альтернативи) та топології.
- Домен і оператор, резервний майданчик, гарантії роботи під час війни, відновлення доступу.
- Процедура захисту від ботів без виключення законних учасників.
- Реальна юридична особа або інший правомірний оператор персональних даних.
- Перевірка громадянства, територіальної належності та прав у офіційних процедурах.
- Повноцінна інформаційна безпека, відповідний аудит і віддалений OAuth MCP.

Жоден із цих пунктів **не реалізований** тільки через ухвалення ADR.

## Критерії приймання для майбутнього пілота

Тести на issuer/audience confusion, відхилення незавершеного PKCE, nonce/state mismatch, session fixation та revocation; перевірка різних клієнтів; незалежний аудит ключів і прав; відсутність будь-яких залежностей від Wesfin; відновлення після відмови; доступність реєстрації; privacy impact assessment; documented incident response.

## Нормативні технічні орієнтири

- [OpenID Connect Core](https://openid.net/specs/openid-connect-core-1_0.html) – перевірка токенів та pairwise subject identifiers.
- [OAuth 2.0 Security Best Current Practice, RFC 9700](https://www.rfc-editor.org/rfc/rfc9700.html) – захист authorization code, redirect URI й PKCE.
- [Model Context Protocol: specification](https://modelcontextprotocol.io/specification/) – актуальні профілі інструментів і авторизації MCP.

Вибір ПЗ і його розгортання є **окремим інфраструктурним рішенням**. Цей документ фіксує незалежність, межі довіри та вимоги для команди, яка вже опрацьовує інфраструктуру.
