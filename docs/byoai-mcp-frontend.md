# RFC-UAGP-0004 — Bring Your Own AI (BYOAI) + MCP + Web Portal

**Статус:** дослідницький MVP; без виробничої сертифікації. Гілка feat/byoai-frontend-mcp, побудована поверх Citizen AI Assistant PR #9, який залежить від PR #8 і PR #7.

## 1. Принцип

Громадянин приходить із власним інструментом: ChatGPT, Claude, локальна LLM, браузерний застосунок чи інше середовище. UAGP **не купує і не контролює** його мовну модель, не збирає її ключі чи розмови. Замість створення ще одного обов'язкового чат-бота UAGP пропонує відкритий контракт для громадянських ідей, MCP-міст для сумісних клієнтів і вебпортал як універсальний спосіб перевірки пропозиції.

BYOAI не означає, що оплачена підписка на AI дає окремий API-ключ. Це залежить від умов провайдера, клієнта, тарифного плану й підтримки MCP. UAGP не бере на себе оплату сторонньої моделі.

## 2. Площини системи

**Personal AI:** громадянин самостійно обирає модель, її провайдера, мову й спосіб зберігання бесід. Особистий застосунок може використати MCP-інструмент \`prepare_civic_proposal\` для отримання структурованого JSON.

**Federation contract:** \`uagp.civic.handoff.v1\` містить тільки категорію, територіальний масштаб, проблему, бажаний результат, можливе рішення та попередню правову категорію. Він не містить імені, ключів, контактів, підтверджень публікації чи прав на дію.

**UAGP Portal:** приймає JSON через імпорт або ручну форму; громадянин бачить і перевіряє текст. Локальний сервер з окремим демонстраційним операторським токеном створює приватну чернетку, а автор за окремим ключем уточнює, підтверджує та створює тестову справу. Приватна справа і публічна картка залишаються різними об'єктами.

**Public catalogue:** доступний лише публічно погоджений вміст: категорія, масштаб, коротке публічне резюме, випадковий ID та демо-статус. Немає доступу до приватних чернеток чи історії AI.

**Future legal workflow:** юридична ідентифікація, повноваження органів, офіційні звернення й державні рішення потребують окремих законних інтеграцій. У MVP відсутні.

## 3. Як підключити власний AI

Початковий MCP працює локально через stdio, а не через незахищений публічний HTTP endpoint.

\`\`\`sh
git clone https://github.com/ailubes/uagp.git
cd uagp
git checkout feat/byoai-frontend-mcp
python -m pip install -e ".[mcp]"
python -m uagp.mcp_server
\`\`\`

Остання команда запускає stdio-процес і призначена для запуску **самим MCP-клієнтом**, а не для взаємодії через термінал. Типова схема конфігурації локального клієнта, який підтримує \`mcpServers\`:

\`\`\`json
{
  "mcpServers": {
    "uagp": {
      "command": "python",
      "args": ["-m", "uagp.mcp_server"],
      "env": {}
    }
  }
}
\`\`\`

Python має запускатися в середовищі, де встановлено UAGP; на деяких системах потрібно вказати абсолютний шлях до Python з virtualenv. Конфігурація є прикладом, а не універсальним форматом для всіх AI-клієнтів: ChatGPT, Claude, IDE й інші продукти мають різні механізми підключення. Користувач може не мати можливості додати власний локальний MCP у конкретному клієнті або плані.

Під час тестування власний AI отримує інструменти \`prepare_civic_proposal\`, \`explore_public_proposals\` та \`explain_uagp_participation\`. Користувач може попросити: «Допоможи сформулювати ініціативу щодо автобусних пересадок у громаді і підготуй UAGP JSON, не подавай нічого». Після відповіді слід скопіювати \`handoff\` у портал.

## 4. Публічний вебфронтенд

Локальний запуск:

\`\`\`sh
docker compose up --build
\`\`\`

Портал першої тестової громади: \`http://127.0.0.1:8001/ui\`; другої громади: \`http://127.0.0.1:8002/ui\`. Ці URL лише локальні; жодного публічного сайту тут не розгорнуто.

Портал має два режими: імпорт із «Мій AI / MCP» та ручне заповнення «Без AI». Далі відбувається перегляд полів, явна згода на створення тестової чернетки, окреме підтвердження її змісту й окремі налаштування публікації. Для демонстратора потрібен локальний \`X-Demo-Operator-Token\`, тому **не розміщуйте цей прототип у відкритому інтернеті**. Тестові токени в compose призначені тільки для локального середовища, а не для справжніх громадян.

Приклад \`uagp.civic.handoff.v1\`:

\`\`\`json
{
  "version": "uagp.civic.handoff.v1",
  "category": "transport",
  "scope": "intercommunity",
  "problem": "Автобус систематично прибуває після відправлення електрички.",
  "desired_outcome": "Зменшити час очікування пересадки.",
  "proposed_solution": "Перевірити можливість узгодження розкладів.",
  "legal_kind": "policy_idea"
}
\`\`\`

Жоден MCP-інструмент MVP не має \`submit\`, \`publish\`, \`sign\`, \`approve\`, \`transfer_private_data\` чи доступу до ключів автора, тож AI не може пройти замість нього процедуру підтвердження.

## 5. Спільна робота різних AI

Громадянин А може скористатися ChatGPT, громадянин Б – Claude, а громадянин В – локальною LLM. Усі троє готують той самий формат UAGP, не обмінюючись платними акаунтами чи повною історією чатів. Після особистого підтвердження та незалежної модерації перевірене публічне резюме доступне для пошуку незалежно від обраної моделі.

Наступні можливості (ще **не реалізовані**): федеративне виявлення схожих публічних ініціатив без профілювання авторів; обговорення альтернатив і незалежне визначення пріоритетів; відкрите опрацювання з урахуванням заперечень; офіційні процедури лише за належного правового мандата; модельно-нейтральні тести користі та ChangeProposal → PolicyBundle.

## 6. Модель загроз

\`prepare_civic_proposal\` валідовує контракт, але не прибирає автоматично чутливі дані з тексту проблеми. Люди повинні переглянути його перед імпортом. Не вставляйте паролі, медичні дані, особисті документи, точні приватні адреси та інші непотрібні відомості.

MCP-сервер не має операторських ключів та прав запису. \`explore_public_proposals\` читає лише whitelist відкритих полів з локальної SQLite бази і повертає порожній каталог, якщо вона відсутня. MCP-клієнт не повинен автоматично довіряти всім іншим стороннім MCP-серверам або необмежено викликати інструменти.

Для віддаленого MCP в майбутньому потрібні захищений Streamable HTTP, належна авторизація за сучасною MCP OAuth-специфікацією, PKCE, перевірка аудиторії токенів, клієнтська ізоляція, обмеження частоти, контроль вихідних з'єднань і незалежний безпековий огляд. **Не** виставляйте локальний stdio-процес через HTTP-proxy без цих вимог.

Фронтенд і sandbox ще не придатні для реальних персональних справ. Зокрема, тестова capability автора та загальновідомі Docker-токени не є юридичною ідентифікацією. Приватні дані не повинні передаватися до реального сервісу без правової підстави й аналізу ризиків.

## 7. Як співпрацювати в UAGP

Єдиний стандарт – не спільна модель, а спільні структури даних, правила публічності, повноважень і версій. Люди мають право приносити в UAGP різні AI-клієнти, погоджувати тільки те, що хочуть оприлюднити, та оскаржувати висновки. Той, хто не користується AI, може застосувати ту саму ручну форму.

Портал не має змушувати створювати обліковий запис одного постачальника моделей або платити UAGP за доступ до політичного висловлювання. Реальні офіційні процедури згодом потребуватимуть окремого правового маршруту та надійної ідентифікації, але не монополії на персонального AI.

## 8. Наступні інженерні завдання

Після перевірки MVP слід додати коректне локальне керування особистими авторськими ключами й відновлення сесії, прозорий статус публікації, мобільну доступність та валідацію JSON Schema під час імпорту, залежність від реального серверного підтвердження. Далі – OAuth-захищений remote MCP, реєстр MCP-клієнтів, контроль прав під час будь-якої write-операції, federation catalogue, криптографічні підписи й зовнішній аудит.
